====================================================================
0. НАЗНАЧЕНИЕ ДОКУМЕНТА
====================================================================

Это основное техническое задание для разработки новой мобильной автомобильной игры под рабочим названием Project X. Документ предназначен для Claude как ведущего технического исполнителя и для владельца проекта как руководства по этапам, входным материалам, проверкам и результатам.

Проект создаётся с нуля. Не упоминать какие-либо предыдущие проекты, не импортировать чужую архитектуру, не переносить код или контент из иных игр без отдельного письменного решения владельца.

Главная идея: добиться впечатляющего, убедительного качества автомобиля, материалов, отражений, света и окружения НА РЕАЛЬНОМ ANDROID-УСТРОЙСТВЕ. Красивый скриншот в редакторе недостаточен. Игровые механики, открытый мир и количество автомобилей наращиваются лишь после подтверждения визуального качества и производительности предыдущего этапа.

Нельзя обещать фотореализм на любом смартфоне, одинаковую графику с ПК или заранее гарантировать конкретный FPS. Качество определяется на выбранных тестовых устройствах и согласованных настройках.

====================================================================
1. ТЕХНОЛОГИЧЕСКАЯ ОСНОВА
====================================================================

1.1. Движок: Unity 6.3 LTS (ветка 6000.3.x), конкретный patch фиксируется в README после создания проекта. Не менять версию редактора без согласования.
1.2. Рендеринг: Universal Render Pipeline (URP), актуальная для установленной версии Unity. Не использовать Built-in Render Pipeline, HDRP или URP-пакеты от несовместимых версий.
1.3. Целевая платформа: Android. Windows Editor — рабочая среда, но не критерий финального визуального результата.
1.4. Язык: C#; архитектура на MonoBehaviour, ScriptableObject и стандартных Unity API, без ненужных сторонних зависимостей.
1.5. Основной ввод: сенсорное управление Android; в редакторе — клавиатура и мышь для тестирования.
1.6. Система контроля версий: GitHub-репозиторий, который владелец укажет отдельно. Claude использует ТОЛЬКО фактически доступные материалы и проверяет права использования.
1.7. Использовать Android-совместимые шейдеры, эффекты и API. Запрещено молча включать дорогие desktop-only решения.
1.8. Предпочтительный рендер-путь — URP Forward/Forward+ только после измерений и проверки совместимости с целевыми устройствами. Не выбирать Forward+ автоматически из-за названия.
1.9. Для первичной Android-сборки предпочесть Vulkan/OpenGLES3 по результатам тестов устройств, а не по предположениям; зафиксировать фактический Graphics API и его ограничения.
1.10. Система управления вводом — Unity Input System; настройки проекта и пакеты должны быть согласованы.

====================================================================
2. ПРОДУКТОВОЕ ВИДЕНИЕ
====================================================================

Жанр: премиальная мобильная автомобильная игра с красивыми машинами, свободной ездой, развитием гаража и расширяемым дорожным миром.

Целевая визуальная планка: выразительный автомобильный лак, физически правдоподобные материалы, чёткая геометрия кузова, качественные диски и тормоза, стекло с правильным восприятием глубины, достоверная оптика, красивое освещение, читаемые отражения, убедительный асфальт и атмосферная среда.

Вдохновение по направлению: автомобильная детализация и подача уровня лучших мобильных гонок, красивая среда свободной езды и кинематографичная атмосфера. Не копировать брендинг, интерфейсы, исходные ассеты, код или защищённые художественные решения конкурентов.

Визуальная цель: автомобиль должен выглядеть дорогим и качественным вблизи, с разных углов и при движении, а не только в одном постановочном кадре.

====================================================================
3. НЕПЕРЕГОВОРНЫЕ ПРАВИЛА РАЗРАБОТКИ
====================================================================

A. Android-first: каждое визуальное решение оценивается с точки зрения мобильного GPU, памяти, нагрева и энергопотребления.
B. Одна законченная вертикальная демонстрация лучше десятка недоделанных систем.
C. Никаких массовых функций, открытого мира, трафика, магазина и экономики до успешного завершения ранних визуальных этапов.
D. Вся графика должна иметь настраиваемые уровни качества, а не единственный тяжёлый пресет.
E. Не использовать HDRP, desktop ray tracing, рассчитывать на Lumen/Nanite (это технологии другого движка), тяжёлые screen-space эффекты без Android-проверки.
F. Нельзя менять десятки несвязанных систем ради одной визуальной правки.
G. Не удалять и не перезаписывать пользовательские материалы без резервной копии и явного согласования.
H. Не утверждать «проверено», «работает на Android», «60 FPS», если не было реального теста с результатами.
I. Для любых внешних моделей и текстур фиксировать источник, автора, лицензию и ограничения. Бесплатно скачанный ассет не обязательно разрешён для коммерческой игры.
J. Лицензии на реальные автомобильные марки, логотипы и дизайн кузова — отдельный юридический вопрос. Наличие модели на Sketchfab само по себе не даёт прав на товарные знаки и коммерческое использование дизайна.
K. При недостатке входных данных Claude обязан явно перечислить, что отсутствует, и предложить безопасную заглушку, не выдумывая ресурсы.

ЭТАП 0 — ЧИСТЫЙ ФУНДАМЕНТ

Цель: полностью воспроизводимый чистый URP-проект.

Задачи:
- Зафиксировать версию Unity и пакетов в README.
- Создать структуру Assets/ProjectX и отдельную тестовую сцену.
- Проверить URP Render Pipeline Asset, Quality Settings, Color Space, Graphics Settings, Android Build Settings.
- Выбрать исходный профиль качества для среднего Android-устройства.
- Настроить .gitignore для Unity, не коммитить Library, Temp, Obj, Logs, Build, UserSettings и локальные секреты.
- Создать README, CHANGELOG, список зависимостей и руководство установки обновлений.
- Проверить, что проект открывается без красных ошибок Console.
- Создать минимальную Android-сборку с пустой сценой, когда доступен тестовый телефон.

Результат: воспроизводимая чистая база, готовая к импорту одной машины.
Критерий перехода: проект открывается, материалы URP корректны, ошибок компиляции нет, базовая сборка возможна либо документирована конкретная причина невозможности.

ЭТАП 1 — ОДНА МАШИНА, МАКСИМУМ ВИЗУАЛЬНОГО КАЧЕСТВА

Это главный приоритет всего проекта. Не приступать к полноценному миру раньше завершения этапа.

1.1. Аудит входной модели:
- Проверить лицензию, формат FBX/GLB/GLTF/OBJ, число треугольников, иерархию, UV, нормали, тангенты, масштабы и ориентацию осей.
- Выделить кузов, стёкла, переднюю и заднюю оптику, колёса, диски, тормозные суппорты, шины, салон, пластик, металл, карбон.
- Проверить, есть ли отдельные колёса и корректные pivot для будущей анимации.
- Зафиксировать недостатки исходника. Не обещать исправление геометрии только материалами.

1.2. Материалы:
- Создать отдельные URP-совместимые материалы, не портить оригинальные текстуры.
- Кузов: металлический/неметаллический слой по физически разумной модели, высокий, но не зеркально-пластиковый smoothness, корректный base color, визуально убедительный лак и блики.
- При необходимости разработать мобильный кастомный шейдер с контролируемым clearcoat-like эффектом; обязателен fallback на стандартный URP Lit.
- Стёкла: отдельные материалы, правильный оттенок, прозрачность/отражения, читаемость салона, контроль сортировки прозрачности.
- Карбон: отдельная текстура и шероховатость, без превращения в чёрное зеркало.
- Резина: матовая микрофактура, отличимая от пластика.
- Диски и металлические элементы: реалистичная реакция на свет.
- Фары: стекло, внутренняя геометрия, emissive-элементы, режимы включения; не заменять фары сплошным белым пятном.
- Задние фонари: отдельные материалы и режимы; без неестественного свечения.
- Салон: хотя бы видимые через стёкла поверхности, без пустых дыр и некорректных отражений.
- Настраиваемые цвета кузова через MaterialPropertyBlock или материал-инстансы с учётом SRP Batcher; проверить фактические компромиссы батчинга.

1.3. Свет и отражения:
- Построить компактный автомобильный шоурум/студию с продуманной геометрией и источниками света.
- Применить качественные reflection probes, baked lighting там, где уместно, и мобильные отражательные приёмы.
- Обеспечить видимые, красивые линии бликов на крыльях, капоте, дверях и крыше.
- Настроить HDR skybox/окружение при соблюдении лицензий и мобильного бюджета.
- Ограничить число realtime lights, их дальность, тени и пересечения.
- Настроить tone mapping, exposure, ambient occlusion и bloom только в поддерживаемом и измеренном режиме.
- Не маскировать плохие материалы чрезмерным bloom, контрастом или saturation.

1.4. Демонстрация:
- Одна машина на поворотной платформе или вращение камеры вокруг неё.
- Камера: front 3/4, rear 3/4, side, close-up деталей, свободное вращение и зум.
- Пресеты освещения: дневной нейтральный, студийный, вечерний/ночной — если не выходят за бюджет.
- Переключение цвета кузова и включение фар как демонстрационные функции.
- Возможность сделать одинаковые сравнительные скриншоты до/после.

1.5. Производительность:
- Проверить на реальном Android, а не только в редакторе.
- Замерить FPS, frame time, память, количество draw calls, перегрев, длительную устойчивость.
- Разработать LOD и бюджет текстур; ASTC для поддерживаемых устройств, альтернативы по матрице совместимости.
- Настроить quality tiers: Low, Medium, High, Ultra/Showroom только если позволяет устройство.
- Целевой ориентир: стабильные 30 FPS на согласованном среднем устройстве; 60 FPS — дополнительная цель на мощном, только после измерений.

Результат: «Project X Visual Prototype 1» — одна машина, которую не стыдно демонстрировать крупным планом.
Критерий перехода: владелец одобрил качество, машина выглядит убедительно с нескольких ракурсов, материалы не ломаются на Android, производительность измерена.

ЭТАП 2 — НЕБОЛЬШАЯ КРАСИВАЯ МЕСТНОСТЬ

Цель: показать ту же машину в реалистичной дорожной среде без преждевременного открытого мира.

- Создать короткий законченный участок дороги/прибрежного шоссе/городского квартала; конкретный сеттинг выбирает владелец.
- Асфальт с качественными albedo/normal/roughness, разметкой, бордюрами, тротуарами, дорожными знаками.
- Правдоподобная архитектура, растительность, небо, облака, атмосферная перспектива и цветовая гармония.
- Освещение и отражения должны сохранять качество машины, но оставаться мобильными.
- LOD, occlusion culling там, где это действительно помогает, GPU instancing, light baking, texture atlases и разумное число материалов.
- Никаких бесконечных дорог, мегаполисов, десятков районов и массового трафика на этом этапе.
- Сравнить качество в шоуруме и на улице, устранить резкое падение визуального уровня.

Результат: «Project X Environment Prototype» — одна машина на красивой небольшой карте.
Критерий перехода: цельный внешний вид, отсутствие критических артефактов, приемлемые замеры Android.

ЭТАП 3 — ПЕРВАЯ ИГРАЕМАЯ ВЕРСИЯ

- Управление автомобилем: газ, тормоз, руль, задний ход, ручник.
- Физика с настраиваемыми параметрами, без заведомо нереалистичного поведения и прыжков.
- Камера от третьего лица с плавным следованием, регулировкой дистанции и FOV.
- Сенсорные кнопки Android и тестовое управление на ПК.
- Звук двигателя, переключение передач, скольжение, столкновения — с возможностью отключать эффекты.
- Спидометр, простой HUD, пауза, перезапуск, настройка графики.
- Колёса вращаются и поворачиваются правильно; кузов не проваливается в дорогу.
- Контроль производительности в движении, в том числе при смене ракурса.

Результат: «Project X Driving Prototype» — машина красиво едет по небольшой дороге.
Критерий перехода: управление удобно, графика сохраняется в движении, нет блокирующих ошибок.

6. ГРАФИЧЕСКИЙ СТАНДАРТ PROJECT X
====================================================================

6.1. Машина — главный герой кадра. Любая графическая функция оценивается по тому, улучшает ли она читаемость форм, глубину и реалистичность.
6.2. Кузов не должен быть пластмассовым, полностью хромированным, пересвеченным или визуально плоским.
6.3. Отражения должны поддерживать форму кузова и изменяться осмысленно при вращении камеры.
6.4. Фары должны иметь геометрию и структуру, а не только emissive-плашку.
6.5. Стёкла не должны выглядеть как непрозрачная чёрная краска или исчезать при изменении угла.
6.6. Диски, тормоза, шины и карбон имеют отдельные PBR-характеристики.
6.7. Текстуры не должны размываться на близком плане из-за неразумного импорта/сжатия.
6.8. Силуэт автомобиля и геометрия важнее постобработки.
6.9. Контакт с землёй, тени и ambient occlusion должны создавать ощущение массы.
6.10. Параметры качества должны быть воспроизводимыми: одна и та же сцена и камера дают сопоставимый результат.
6.11. Любой кастомный шейдер требует документирования стоимости, поддерживаемых Android API, fallback и способа отключения.
6.12. Тестировать разные условия освещения; «красиво только ночью» или «только в шоуруме» не считается успехом.

====================================================================
7. МОБИЛЬНАЯ ОПТИМИЗАЦИЯ
====================================================================

С самого начала фиксировать:
- целевые телефоны и их GPU/SoC;
- разрешение экрана и render scale;
- графический API;
- средний FPS и 1% low / frame time;
- CPU main/render thread и GPU frame time (где доступны);
- объём памяти и размер сборки;
- количество draw calls/batches, треугольников, realtime lights;
- качество и количество теней;
- тепловую устойчивость в сессии 10–20 минут.

Принципы:
- Профилировать на устройстве через Unity Profiler/Frame Debugger и доступные GPU-инструменты.
- Использовать baked освещение для статичной среды, когда это выгодно.
- Ограничивать real-time тени и прозрачные материалы.
- Избегать неоправданных fullscreen-pass эффектов и дорогих screen-space отражений.
- LOD0 для шоурума, более дешёвые LOD для дорожной сцены; бюджет назначить после изучения модели и устройства.
- Настраивать anisotropic filtering, mipmaps, ASTC, MSAA и render scale по профилям.
- Не включать динамическое разрешение без тестов качества и совместимости.
- Не объявлять «оптимизировано», пока нет фактических измерений.

Ориентир, не гарантия: 30 FPS на согласованном среднем Android; 60 FPS на мощном устройстве при подходящем пресете.
